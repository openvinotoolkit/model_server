# Запуск больших MoE на Intel Arc 140V: сводка исследований

Дата: 2026-10-06. Статус пометок: [замерено] — чужие или наши измерения,
[дока] — официальная документация, [оценка] — расчёт, [вендор] — цифры вендора,
[проверить] — открытый вопрос.

## 1. Постановка задачи

- Машина: Intel Arc 140V — встройка Lunar Lake (архитектура Xe2), **XMX-блоки есть**,
  память общая с CPU (LPDDR5X, всего 32 ГБ). ОС: Windows 11.
- Бюджет: отдать 27.5 ГБ из 32 ГБ под модель (рекомендация из исследования: закладывать
  25–26 ГБ, оставив системе 6–7 ГБ — ниже обоснование в п. 7).
- Цель: большая MoE (класс Qwen3.6-35B) + максимально длинный контекст.
  Проблема: «квен большой, а контекст выходит маленький» — веса съедают бюджет,
  на KV-кеш почти ничего не остаётся. Решение — офлоад весов экспертов на диск (п. 5).

## 2. Почему не SYCL-порт Strata

- SYCL-порт Strata (`sycl/`, PR #423) спроектирован под дискретную VRAM:
  эксперты стримятся в память карты, везде VRAM-бюджеты и резервы.
- По `docs/INTEL_ARC.md:32`: integrated Arc GPUs (B390 / Panther Lake, issue #515)
  никем не тестировались — **shared-memory planning does not exist yet**.
- Дополнительно: движок Strata зашит под семейство Qwen3.8-Flash-Next
  (GDN, QSA-индексер, PLE-слой, MTP-драфт). Чужую архитектуру он запускать не умеет;
  сетап предлагает только семейства qwen / swift / coder / unsloth.
- Вывод: Strata на Arc-машине не вариант ни для чего, кроме родного семейства
  (которого там нет).

## 3. Кандидаты в рантаймы (Windows 11 + Arc 140V)

| Рантайм | Плюсы | Минусы |
|---|---|---|
| Стоковый OVMS (ovms.exe, `--target_device GPU`) | OpenAI-совместимый API, готовые INT4-сборки на HF (`OpenVINO/*-int4-ov`), continuous batching, tool-calling/MCP, офлоад MoE на диск (п. 5) | Версия критична (нужен 2026.2+); нюансы с длинными промптами (п. 6) |
| Свой форк OVMS (с расширенной Gemma4) | Уже есть, Gemma4 покрыта лучше стока | Проверить версию OpenVINO и покрытие `qwen3_5_moe` |
| llama.cpp, SYCL-бэкенд | Официально поддерживает built-in Arc вкл. Lunar Lake; лучший префилл на Intel ([замерено] на 140V: префилл ~2× от M1 Pro, почти M1 Max) | Нужен oneAPI (~5 ГБ); декод слабый ([замерено]: ~12 ток/с на 7B Q4_K_M — уровень старого M2); сборка под Windows болезненна |
| llama.cpp, Vulkan-бэкенд | Ноль трения (Mesa + бинарник, на Windows проще всего); K-кванты, MoE, int4 KV — всё едет | Префилл заметно ниже SYCL (XMX через Vulkan не задействовать); декод почти паритетный (все упираются в пропускную способность LPDDR5X) |
| IPEX-LLM | INT4/FP4/INT2 из коробки, MoE верифицированы (Mixtral), portable-сборки llama.cpp и Ollama; для встройки советуют `cpu_embedding=True` | Предсобранный llama.cpp от Intel протух (~апрель 2025, нет новых архитектур) — ставить через pip свежий |
| OpenVINO GenAI (Python) | Тот же стек, что OVMS, но с прямым доступом к `OFFLOAD_RATIO` (п. 5) | Не сервер; для сервиса нужен свой обвес |
| NPU Lunar Lake (48 TOPS) | Только мелочь (1–3B INT4) | Для 26–35B irrelevant |
| CPU | Всегда работает | Наymo? Нет: медленно; только фолбэк |

## 5. OFFLOAD_RATIO — офлоад MoE-весов на диск (ключевая фича)

- Что: проперти GPU-плагина OpenVINO 0–100 = % экспертов MoE, живущих НЕ в памяти,
  а подтягиваемых с диска через LRU-кеш (PR openvino#36202, релизы 2026.3+).
  [дока] `src/plugins/intel_gpu/include/intel_gpu/runtime/options.inl`:
  «Percentage (0-100) of model weights to offload to disk. Currently supported
  for MoE experts only.»
- Замеры [замерено] (Qwen3-30B-A3B INT4):

| offload | резидентно | декод |
|---|---|---|
| 30 | 10.8 ГБ | 25.3 ток/с |
| 50 | 8.1 ГБ | 22.1 ток/с |
| 90 | 2.35 ГБ | 5.1 ток/с |

- Жёсткое требование: **только XMX-залезо** (Arc-дискретки, Lunar Lake, Panther Lake).
  На без-XMX встройках (десктопные Arrow/Meteor Lake) — тихий no-op, без ошибки.
  Arc 140V XMX имеет — заведётся. [дока + замерено]
- Python API (подтверждённый синтаксис) [дока]:
  `ContinuousBatchingPipeline(models_path, device="GPU", properties={"OFFLOAD_RATIO": "37"})`
- Синтаксис для OVMS CLI/конфига — [проверить] (в исследовании не подтверждён,
  не выдумывать; вероятное место — `plugin_config` модели).
- Важно для нашей арифметики: Qwen3.6 int4 (~20 ГБ) влезает в 27.5 ГБ и так.
  Офлоад нужен, только если: (а) отдавать больше RAM под KV/длинный контекст,
  (б) замахиваться на модель больше бюджета (ценой падения до ~4–5 ток/с).

## 6. Что говорит стоковый OVMS (по докам, без запуска)

- [дока] Готовая сборка `OpenVINO/Qwen3.6-35B-A3B-int4-ov`; в демо agentic_ai прямо:
  «Requires OpenVINO 2026.2+, tested on PantherLake iGPU with 32GB RAM
  with iGPU allocation increase and B70 dGPU» — ровно наш сценарий.
- Деплой: `ovms.exe --source_model OpenVINO/Qwen3.6-35B-A3B-int4-ov
  --model_repository_path <MODEL_REPOSITORY> --rest_port 8000 --target_device GPU`.
  Выбор устройства автоматический (dGPU → iGPU → CPU); на машине без дискретки
  возьмёт встройку сам. Windows 11 + `ovms.exe` — штатный путь (Docker с GPU
  на Windows только через WSL2 `/dev/dxg`, натив проще).
- Известные проблемы [дока]:
  - Qwen3-MoE INT4 на GPU теряет точность на длинных промптах; воркаунд:
    `MOE_USE_MICRO_GEMM_PREFILL=0` (чуть растёт TTFT). Наши промпты 50–100K —
    в зоне риска, проверить needle-тестом.
  - Валидация MoE — промпты 1K–32K. Длинные контексты за пределами CI Intel.
  - В старых версиях MoE для Qwen3.5/3.6 и Gemma 4 — без continuous batching;
    в свежих Qwen3-MoE уже с ним. Брать 2026.4 / latest-gpu.
  - Есть пре-оптимизированные Qwen3-MoE и GPT-OSS на HF, MTP/DFlash-спекуляция
    для Qwen3.6, тул-парсеры для Gemma 4.

## 7. Арифметика памяти (бюджет 27.5 ГБ) [оценка]

- Qwen3.6-35B-A3B int4: ~20 ГБ весов → ~7 ГБ остаётся под KV + рантайм.
  GDN-гибрид (как у Flash-Next: лишь часть слоёв — полный attention) даёт
  маленький KV на токен — длинные контексты (100K+) должны влезать в единицы ГБ.
- Но: системе, драйверу и рантайму нужно 2–3 ГБ; спайк аллокации = OOM.
  Поэтому рекомендация — отдавать под модель 25–26 ГБ, не 27.5.
- Если контекст всё равно маленький выходит: крутить `OFFLOAD_RATIO` вверх
  (резидентно 8–10 ГБ) и отдавать высвобождённое под KV, либо ужимать модель
  (Gemma-26B: 14.4 ГБ весов — запас огромный).

## 8. План действий

1. Поставить нативный `ovms.exe` (2026.4+), Intel Graphics драйвер с HF.
2. Запустить `OpenVINO/Qwen3.6-35B-A3B-int4-ov`, `--target_device GPU`.
3. Прогнать needle-in-haystack на 32K → 100K+ (метод: спрятать passkey в документ
   известной длины через `/v1/messages/count_tokens`-аналог, спросить retrieval;
   матрица: длины × глубины 0/25/50/75/100%).
4. Если длинные промпты плывут — `MOE_USE_MICRO_GEMM_PREFILL=0`.
5. Если RAM впритык — докопать синтаксис `OFFLOAD_RATIO` для OVMS и поднять ratio.
6. Фолбэки по убыванию: свой форк OVMS (Gemma4-26B) → llama.cpp SYCL →
   llama.cpp Vulkan → IPEX-LLM.

## 9. Открытые вопросы (для второго ассистента / ручной проверки)

1. Точный синтаксис `OFFLOAD_RATIO` в OVMS (CLI-флаг vs `plugin_config` в config.json).
2. Реальная скорость и needle на 140V именно с Qwen3.6-35B (замеров на этой связке
   в паблике нет; ближайший аналог — Qwen3-30B-A3B на 140T).
3. Версия OpenVINO в своём форке OVMS и покрытие `model_type=qwen3_5_moe`
   (по optimum-intel#1754 экспорт падал на старых версиях; нужен transformers ≥5.5).
4. GGUF-квант Qwen3.6-35B-A3B под llama.cpp-фолбэк (проверить наличие на HF).
